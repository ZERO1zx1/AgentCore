# Adaptive routing reference

Identify required capabilities before choosing a tool or model: deterministic execution, repository context, coding language, vision/layout, audio/video, browser/tool access, structured output, privacy, latency, and cost. Filter incapable routes first; cheap retries are not efficient.

For non-trivial work keep a compact record: objective, workspace evidence, reversible assumptions, P0–P4 units, validation/checkpoint, limits, completed evidence, and next action. Validate changed producer-to-consumer boundaries (for example source → build → runtime) rather than unrelated subsystems. Escalate only after a concrete capability gap; de-escalate once deterministic tooling can finish.

## Memory and route contracts

1. Admission rejects vague, unevidenced, sensitive, or policy-manipulating lessons.
2. Recall returns a score breakdown and dry-run explanation before planning.
3. Conflicting hints are disclosed; lower-ranked conflicting hints are suppressed.
4. Provenance links task/source fingerprints, checkpoint, validation, and artifacts.
5. Fingerprint or policy-version drift moves verified lessons to stale.
6. Hybrid retrieval combines lexical scoring with an optional offline semantic backend.
7. Capability health records success, latency, and honestly attributed cost by route.
8. Fallback never repeats an unchanged failed paid route and protects the reserve.
9. Cross-task metrics keep estimates separate from provider-confirmed values.
10. Deduplication proposes canonical clusters without erasing audit history.
11. Knowledge packs are scoped, sanitized, versioned, and hash-verified.
12. Reader, contributor, reviewer, and maintainer roles gate memory actions.
13. Poisoning detection blocks instructions that try to bypass policy or validation.
14. Review cards expose use, ignore, stale, retire, and evidence decisions.
15. Replay runbooks contain explicit preconditions, steps, validation, and outcomes.
